# AGENTS.md

## Repository purpose

`snakepit` is a lightweight, portable Python/JupyterLab environment for experimentation, tutorials, data work, APIs, and GIS workflows.

It is intended to be:

* easy to clone onto a new machine
* reproducible with `uv`
* usable on Linux, WSL, and macOS
* lightweight enough for quick experiments
* flexible enough to accumulate broadly useful Python dependencies
* editor-independent, with JupyterLab as the primary interface

This is a personal workbench, not a production Python package.

## Environment

Python is managed with `uv`.

The project currently targets Python 3.12+ and pins Python 3.12 through `.python-version`.

Primary environment files:

* `pyproject.toml` — declared dependencies
* `uv.lock` — reproducible dependency lockfile
* `.python-version` — preferred Python version
* `.venv/` — local virtual environment; never commit

To create or update the environment:

```bash
uv sync
```

To run JupyterLab directly:

```bash
uv run jupyter lab
```

The convenience launcher is:

```bash
./lab.sh
```

`lab.sh` sets the repository-local JupyterLab settings directory and launches JupyterLab with automatic confirmation enabled.

## JupyterLab configuration

Portable JupyterLab preferences live under:

```text
jupyter-settings/
```

`lab.sh` sets:

```bash
JUPYTERLAB_SETTINGS_DIR="$PWD/jupyter-settings"
```

This allows interface preferences to travel with the repository.

Current intentional settings include:

* JupyterLab Dark theme
* notebook code-cell line numbers
* Jupyter news notifications disabled

When modifying JupyterLab preferences, prefer storing only intentional overrides rather than committing a complete copy of every default setting generated by JupyterLab.

## Dependency policy

Use `uv` project commands rather than directly manipulating `.venv`.

For persistent dependencies:

```bash
uv add PACKAGE
```

For removing dependencies:

```bash
uv remove PACKAGE
```

For temporary experiments, prefer ephemeral `uv` execution where practical rather than permanently modifying the project.

Avoid:

```bash
uv pip install PACKAGE
```

for normal project dependency management, because it can mutate `.venv` without recording the dependency in `pyproject.toml`.

Dependencies that become broadly useful for experimentation are welcome in `snakepit`; the goal is not to keep the dependency list artificially minimal.

If an experiment develops substantial or conflicting dependency requirements, recommend promoting it to its own project rather than distorting the shared `snakepit` environment.

The environment includes tools for:

* JupyterLab
* IPython / ipykernel

### Data analysis

* NumPy
* pandas
* Matplotlib

* DuckDB

### APIs and validation

* requests

### GIS

* GeoPandas

Avoid adding the Python `gdal` package casually. Prefer higher-level packages such as GeoPandas, Rasterio, Pyogrio, Shapely, and PyProj unless direct GDAL bindings are specifically required.

## Coding philosophy

This repository is primarily for exploratory work.

Favor:

* readable code
* explicit experiments
* small notebook cells
* comments that explain non-obvious reasoning
* straightforward Python over unnecessary abstraction
* reproducible examples
* moving reusable code into `.py` modules when a notebook starts becoming unwieldy

Do not prematurely turn notebook experiments into application architecture.

If code clearly grows beyond experimentation, suggest extracting it into a separate project.

## Python style

Prefer modern Python 3.12 syntax where useful.

General conventions:

* follow PEP 8
* use descriptive names
* use f-strings
* prefer `pathlib.Path` over manual path-string manipulation
* use type hints when they clarify interfaces or data structures
* prefer Pydantic models when validating structured external data
* avoid unnecessary classes
* keep functions focused and testable
* use `with` blocks for files and other managed resources

Do not add formatting, linting, or testing infrastructure unless it is useful for actual code being developed.

## Notebook conventions

Notebooks are allowed to be exploratory and imperfect.

When editing notebooks:

* preserve Markdown explanations when they provide useful context
* avoid gratuitous reformatting of unrelated cells
* do not remove outputs unless there is a reason
* do not introduce notebook-output stripping tools without discussion
* avoid committing huge binary outputs or embedded datasets unnecessarily
* use Markdown cells to record conclusions that may be useful later

A notebook may retain outputs when they are useful documentation of an experiment.

## Data and generated files

Do not assume directories named `data/`, `output/`, or similar should be ignored.

Small datasets, GeoJSON files, CSVs, generated figures, and other artifacts may legitimately be part of a reproducible notebook.

Do not add broad ignore patterns such as:

```gitignore
*.csv
*.json
*.tif
*.gpkg
```

without a concrete reason.

Prefer targeted ignores for genuinely local, large, sensitive, or disposable material.

## Secrets

Never commit credentials, API keys, tokens, passwords, or private connection information.

If an experiment requires secrets, recommend environment variables or a local `.env` file and ensure the secret-containing file is ignored before use.

## Cross-platform concerns

The repository should remain usable on:

* WSL/Linux
* macOS
* other standard Unix-like Python environments

Avoid hard-coding machine-specific absolute paths.

Use `pathlib` and repository-relative paths where possible.

Do not commit `.venv`.

Be cautious when adding packages with platform-specific native dependencies. Verify that additions remain reasonably installable on both Linux and macOS.

The launcher uses Bash:

```bash
#!/usr/bin/env bash
```

This is intentional and is compatible with macOS systems whose interactive shell is zsh.

## Git practices

Do not modify unrelated files merely to make the working tree look cleaner.

Before making significant changes, inspect the current state of the repository.

When suggesting a commit after completing work, provide a concise commit-message suggestion. Do not explain basic `git add`, `git commit`, signing, or `git push` procedures unless explicitly asked.

Never rewrite published history or force-push unless explicitly requested.

## When working in this repository

Before implementing a larger change:

1. inspect `pyproject.toml`
2. inspect relevant notebooks or source files
3. preserve the lightweight, exploratory character of the repository
4. avoid unnecessary infrastructure
5. explain any dependency or architectural change that materially affects portability

When a request is ambiguous, prefer the smallest reasonable implementation that preserves flexibility.

The central goal is that `snakepit` remains a pleasant place to quickly try Python code without turning into a complicated platform that itself needs maintenance.

## Collaboration, reasoning, and communication expectations

* Do not guess when a factual answer can reasonably be verified. Prefer primary and authoritative sources, especially official documentation, release notes, standards, and source code. For consequential, uncertain, or contested claims, seek corroborating evidence when practical. For technology and dependency questions, favor current documentation and identify relevant recent changes, deprecations, or version-sensitive behavior.

* Critically evaluate important reasoning and recommendations before presenting them as sound. Identify weak assumptions, missing evidence, overlooked tradeoffs, and information that may be incomplete or outdated. When the consequences warrant it, stress-test ideas with difficult questions, plausible counterexamples, and realistic failure scenarios.

* If a request is ambiguous enough that plausible interpretations could produce materially different results, ask two or three focused clarifying questions before proceeding. Otherwise, make a reasonable, clearly stated assumption and complete the smallest useful scope without imposing unnecessary checkpoints.

* For larger, uncertain, or exploratory work, proceed incrementally and provide natural opportunities for feedback, experimentation, and course correction. Small, clearly scoped, low-risk tasks may be completed directly or introduced as short, numbered sequences of tasks.

* For nontrivial, uncertain, or risky changes, diagnose and explain the issue before proposing an edit. Distinguish verified facts from inferences, and separate confident recommendations from unresolved questions. Identifying a possible improvement does not by itself authorize a repository change.

* Before adding new logic, search the codebase for related implementations, established patterns, tests, and edge cases. Follow existing project conventions unless there is a clear reason to depart from them, and avoid reformatting or changing unrelated code.

* Keep the current objective in focus. Briefly identify useful but unrelated ideas and suggest recording them for later consideration. A GitHub Issue may be appropriate for a concrete bug, enhancement, or dependency need, but do not create one without explicit approval.

* Treat discussions of Python, data science, geospatial analysis, structured metadata, data engineering, APIs, and related technologies as continuing professional education. Assume substantial Python experience and expert GIS knowledge. Explain underlying concepts, reasoning, and tradeoffs; highlight deeper topics and useful interdisciplinary connections when relevant; and keep sidebars connected to the active task. Avoid unnecessary beginner framing.

* For particularly complex, confusing, or lengthy topics, include a brief `tl;dr` or `ELI5` summary when it would improve understanding. Treat this as a plain-language reframing, not beginner-level instruction: respect existing knowledge and expertise while minimizing jargon, shorthand, and unnecessary technical detail.

* Prefer concise, direct conversation. Lead with the practical conclusion, explain material tradeoffs, and avoid long multipart plans unless the scope genuinely requires one.

* Use American English and Oxford commas in prose. Treat tabs in user messages as an input habit, not as a file-formatting requirement. Where the project uses them, format Python with Black and Ruby or Ruby on Rails code with StandardRB. Do not introduce formatter configuration or reformat unrelated code without discussion.
